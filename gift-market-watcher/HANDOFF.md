# HANDOFF — gift-market-watcher

Контекст для новой сессии Claude Code (например, на сервере Дима). Прочитай целиком перед работой.

Пользователь — Дим. Общаемся на «ты», по-дружески. Он хочет обсуждать идеи вместе и слышать нестандартные предложения.
Часто пишет с телефона: команды давай короткими, по одной.

---

## Цель

Свой «see.tg» (live.see.tg, @seetgbot): собирать все события NFT-подарков Telegram в свою базу и отдавать людям из неё.
Сюда входят листинги, смены цен, продажи, снятия, а позже передачи, выпуск, владельцы, флоры по атрибутам, уведомления, Mini App и API.
Интеграция с GiftFit (отдельный проект Дима) — флоры по комбинациям, события в 3D-мире.

Конкуренты:
- see.tg: ~13 млн гифтов, скан раз в ~минуту, 100 аккаунтов, 415 млн событий, ~48 соб/с. Атрибуты берут из API @GiftChanges. Есть рукопожатия, лидерборды, флоры, статусы, API.
- Telegifts (iOS/Android, Maxim Novikov): нативное приложение, виджеты, Apple Watch, портфель через вход в Telegram.

## Что уже построено (папка `gift-market-watcher/`, ветка `claude/parser-from-chat-k5im4d`)

```
сборщики → Redis Streams → нормализатор → Postgres → API (REST + WS /live)
```

- `gmw/collectors/market.py` — `MarketCollector` поверх любого источника (протокол `MarketAPI`: catalog / page / gift_state).
  - Горячий скан: первая страница коллекции (без sort_by_* сервер сортирует по времени изменения цены). Интервал адаптивный в пределах [hot_min, hot_max].
  - Полный скан: все страницы по `sort_by_num` с защитами (повтор курсора, пустая страница с курсором, лимит страниц, сверка с count). Незавершённый обход пропавших не трогает. Завершённый проверяет их через `getUniqueStarGift`: сменился владелец → owner_changed (НЕ sold: может быть передача), нет → delisted, не найден → gone.
  - Первый полный скан коллекции — посев (`seed`) без событий.
- `gmw/collectors/telegram.py` — источник Telegram на Telethon (`getStarGifts`, `getResaleStarGifts`, `getUniqueStarGift`). **Ещё ни разу не гонялся на живом Telegram.**
- `gmw/collectors/fake.py` — фейковый маркет для разработки и тестов.
- `gmw/accounts.py` — пул аккаунтов: запросы по кругу, пауза между запросами, при FLOOD_WAIT аккаунт отдыхает.
- `gmw/differ.py` — снимки → события listed / price_changed (только родная цена продавца; TON-пересчёт по курсу не событие) / owner_changed / delisted / gone.
- `gmw/storage.py` + `schema.sql` — события с детерминированным id (дедуп). Проекции listings (с `active` и метками времени, чтобы повторная доставка ничего не ломала) и gifts. Коллекции.
- `gmw/worker.py` — нормализатор. `gmw/api.py` — `/events`, `/gifts/{slug}`, `/floors`, `/stats`, `WS /live`, опциональный токен `GMW_API_TOKEN`.
- `bench.py` — отдельный скрипт-замер маркета (сколько лотов, длительность цикла, флуд-лимиты).
- `deploy/preflight.sh` (только читает) и `deploy/install.sh` (одна папка, compose-проект `gmw`, API на 127.0.0.1:8040). `docker-compose.yml` с лимитами памяти и CPU и ротацией логов.
- Тесты: `pytest` — 11 юнит-тестов. Сквозной тест конвейера запускается с `GMW_TEST_DATABASE_URL` и `GMW_TEST_REDIS_URL`, **он чистит таблицы и Redis — давай ему отдельную пустую базу и отдельный номер БД Redis**.
- Демо на фейковых данных: https://claude.ai/artifact/Q7KuGLycowkhu8ntm5NwCY

## Замер 04.10 (bench, один свободный аккаунт, делал GPT на маке Дима)

- 121 коллекция на маркете (в каталоге GiftFit 151 — причина расхождения не выяснена), ~777 тыс. лотов → ~7.8 тыс. страниц.
- Задержка ~490 мс (p95 ~600). Пауза 0.1 с → FLOOD_WAIT 37 с на 41-м запросе. Пауза 1.5 с → 81 запрос без флуда (~29 стр/мин).
- Не измерено: независимость лимитов разных аккаунтов, долгий темп, глубокая пагинация sort_by_num на живых данных.
- Рабочая служба GiftFit: `giftfit-continuous-market-recovery-20261004-v2.service`, 61 аккаунт, сейчас последовательно с общим интервалом 3 с. НЕ трогать.

## Ревью GPT (04.10) и что исправлено

1. Сборщик был последовательным → параллельный диспетчер (`run(workers, max_full)`), пул — один запрос на аккаунт.
2. sold по смене владельца → `owner_changed`; owner_name больше не идентификатор; ошибка проверки = неизвестно (исключение).
3. TON-пересчёт давал ложные price_changed, терялись nanos → родная цена (`ton_only`), дробные звёзды.
4. Не было защиты курсоров/полноты → проверки в `scan_all`, незавершённый обход не снимает лоты, точечная проверка обновляет цену.
5. Telethon молча спал на флудах < 60 с → `flood_sleep_threshold=0`, `request_retries=1`; сроки флуда в `flood_state.json`.
6. Снимок обновлялся до отправки → сначала атомарная отправка пачки, потом снимок.
Открыто: подтверждение продаж (кандидат — `payments.getUniqueStarGiftValueInfo`, не проверен вживую).

## Повторное ревью GPT (05.10) и что исправлено

1. Флуды: сроки хранятся отдельно от паузы, по (аккаунт, метод); короткий флуд при длинной паузе не теряется;
   повреждённый файл — отказ стартовать; передача запроса другому аккаунту настраивается (`GMW_REROUTE_ON_FLOOD`);
   отмена посреди запроса освобождает аккаунт (исход — unknown, без повтора).
2. `request_retries=1` в Telethon = 2 отправки (подтверждено тестом на настоящем `_call`) → везде `request_retries=0`.
3. Доставка: локальное состояние сборщика `gmw/state.py` (SQLite) — снимок + outbox одной транзакцией,
   отправка из outbox до подтверждения с теми же id. Закрыты сценарии: шина лежит и рынок вернулся назад,
   потерян ответ шины, рестарт сборщика до обработки воркером.
4. Изменение только котировок (курс) → сообщение `quotes`, база обновляет цены лота без события.
5. Полный обход: статусы duplicates / order / count_drift / short, честный допуск 2% (ceil), complete только при согласованности.
P2: отмена в пуле, ton_only=None, когда поля нет (а не False), XAUTOCLAIM зависших сообщений в Redis.
Не делалось (осознанно): Decimal вместо float для звёзд (нужны суммы > 10^7 звёзд с nanos, чтобы потерять точность).
bench.py переписан: одна отправка, дедлайн и резерв, стоп на unknown, отчёт в finally, без имени/UID/владельцев,
`--login` отдельно, `--collection`, `--min-lots`, правильный p95; 7 тестов в tests/test_bench.py.

## Договорённости

- Только запасные аккаунты Telegram, не основной. Ключи и сессии — только в `.env` и `sessions/` на машине, никогда в чат и в git.
- Не покупать «старые» аккаунты (часто угнанные, против правил Telegram). Если нужно больше аккаунтов — свои SIM или eSIM, либо анонимные номера +888 с Fragment.
- **Сервер общий, на нём другие проекты.** Работать только в своей папке. Чужие контейнеры, nginx, firewall, systemd не трогать.
  Перед любыми изменениями вне папки проекта спрашивать Дима.
- На сервере уже есть **другой NFT-проект Дима с аккаунтами**. Его код можно читать и брать нужное.
  Аккаунты из него не использовать одновременно с его работающим парсером: общие лимиты, FLOOD_WAIT ударит по обоим.
  Сначала спросить, какие аккаунты свободны. Ничего в том проекте не менять без явного «да».

## Что делать первым делом на сервере

1. Посмотреть существующий NFT-проект Дима: что он уже собирает, какие методы и аккаунты использует, что из этого переиспользовать.
2. `bash deploy/preflight.sh` — проверить ресурсы, Docker и порт.
3. Прогнать `bench.py` от свободного аккаунта, разобрать `bench_out/report.json`: число лотов, горячий цикл, запросов на полный цикл, где начинается флуд.
4. По цифрам выставить `GMW_HOT_MIN/MAX`, `GMW_FULL_INTERVAL`, число аккаунтов. Поднять `install.sh` → `login` → `--profile telegram`.
5. Проверить на живых данных: `/stats`, `/events?type=owner_changed`, `/floors`, `/floors/{id}?by=model,backdrop`.
