# Тестовый прогон на реальных подарках — инструкция для ассистента

Привет! Этот пакет передаёт Дим. Скрипт `bench.py` один раз замеряет **маркет перепродажи NFT-подарков Telegram**.
Цифры нужны, чтобы настроить постоянный сборщик (листинги, смены цен, продажи, снятия).

## Что делает скрипт

Он **только читает**: ничего не покупает, не выставляет, не пишет в чаты и ничего не меняет в аккаунте.
Методы MTProto через Telethon:
1. `payments.getStarGifts` — каталог коллекций. Поля `availability_resale` (сколько на продаже) и `resell_min_stars` (флор).
2. `payments.getResaleStarGifts` по каждой коллекции, первая страница — «горячий» скан. Без `sort_by_*` сервер отдаёт лоты по времени последнего изменения цены, новые сверху.
3. Ограниченный полный обход: пагинация по `next_offset`, не больше `--full-budget` запросов (по умолчанию 300).

На первом `FLOOD_WAIT` скрипт останавливается и всё равно пишет отчёт (флаг `--wait-on-flood` — ждать и продолжать). Telethon настроен так, что сам на флудах не спит и запросы не повторяет.
Полный обход идёт с `sort_by_num` и отмечает для каждой коллекции статус: `complete`, `repeated_cursor`, `empty_page_with_cursor`, `budget`, `stopped`.

## Правила (важно, на сервере есть другой рабочий проект)

- **Не меняй существующий проект.** Скрипт запускается из этой отдельной папки, в своём venv.
- **Аккаунт.** Нужен запасной аккаунт, который **сейчас не используется работающим парсером**: одновременные запросы с одного аккаунта делят лимиты, и FLOOD_WAIT ударит по обоим. Спроси Дима, какой аккаунт свободен.
- **Сессия.** Скрипт на **Telethon**. Подойдёт `.session` от Telethon. **Скопируй** её сюда, не трогай оригинал:
  `cp /путь/к/проекту/sessions/<аккаунт>.session ./bench.session`.
  Сессия от Pyrogram или другой библиотеки не подойдёт. Тогда при первом запуске Дим войдёт заново (номер, код, 2FA), и появится `bench.session`.
- Не публикуй и не пересылай `.env` и `*.session`: это полный доступ к аккаунту.

## Скачать (репозиторий публичный)

Код: https://github.com/GreenFather7/Share/tree/claude/parser-from-chat-k5im4d/gift-market-watcher
Нужен только `bench.py` и эта инструкция:

```bash
mkdir -p ~/gift-bench && cd ~/gift-bench
B=https://raw.githubusercontent.com/GreenFather7/Share/claude/parser-from-chat-k5im4d/gift-market-watcher
curl -fsSLO $B/bench.py && curl -fsSL $B/BENCH.md -o INSTRUCTION.md
printf 'TG_API_ID=\nTG_API_HASH=\nTG_SESSION=bench\n' > .env.example
```

## Запуск

```bash
cd ~/gift-bench
python3 -m venv .venv && source .venv/bin/activate
pip install "telethon>=1.40" "python-dotenv>=1.0"
cp .env.example .env      # вписать TG_API_ID, TG_API_HASH; TG_SESSION=bench (имя файла без .session)
python bench.py --login   # только если сессии ещё нет: вход (номер, код, 2FA), замер не выполняется
python bench.py           # каталог + горячий скан + полный обход (бюджет 300 запросов), пауза 1.5 с, дедлайн 10 мин
```

Правила безопасности, встроенные в скрипт:
- ровно одна отправка на запрос (`request_retries=0`), Telethon сам на флудах не спит (`flood_sleep_threshold=0`);
- первый `FLOOD_WAIT` или любая непонятная ошибка или таймаут — стоп, новых запросов нет, отчёт пишется всё равно;
- общий дедлайн `--max-seconds` (по умолчанию 600); перед каждым запросом на ответ остаётся `--reserve` (30 с);
- в отчёт и на экран не попадают имя и UID аккаунта и владельцы лотов.

Варианты:
```bash
python bench.py --hot 0 --collection <id> --full-budget 400   # полный обход одной коллекции (id печатается в каталоге)
python bench.py --hot 0 --min-lots 1000 --full-budget 400     # полный обход, начиная с коллекций от 1000 лотов
python bench.py --delay 2 --max-seconds 600                   # долгий прогон на паузе 2 с
```

Статусы полного обхода по коллекции: `complete`, `repeated_cursor`, `empty_page_with_cursor`, `duplicates`,
`order` (номера не по возрастанию), `count_drift` (количество от сервера плыло), `short` (собрано меньше
количества), `budget`, `stopped`.

## Что вернуть Диму

1. Итог из консоли (блок «===== ИТОГ =====»).
2. Файл `bench_out/report.json` целиком, по каждому прогону. Ключей и личных данных в нём нет, только цифры по маркету.
3. Любые ошибки целиком (traceback).

Интереснее всего:
- `estimate.total_listings` — сколько лотов на маркете;
- `estimate.hot_cycle_sec` — сколько длится горячий цикл на одном аккаунте;
- `estimate.full_cycle_requests` и `full_cycle_sec_one_account` — сколько запросов и времени уходит на полный обход;
- `stats.flood_waits` — на каком запросе и на сколько секунд прилетел флуд;
- `stats.latency_avg_ms` и `latency_p95_ms` — задержка запросов.

## Проверь заодно (поможет нам)

- В `bench_out/snapshot.json` у лотов заполнены `stars` или `ton`? Если цена везде `null`, значит, поля в этой версии схемы называются иначе. Посмотри, какие атрибуты есть у объекта `StarGiftUnique`, и сообщи.
- Заполнено ли поле `owner`? От него зависит, сможем ли мы отличать продажу от снятия.
- Если в существующем проекте уже есть свой способ получать маркет (другие методы, внешние API Portals, MRKT, Tonnel), опиши его коротко: возможно, что-то возьмём.
